# Research protocol

## 0. Intake and capability check
Record the user's target and goal (proof, disproof, bound or selection), harness revision, actual tools and constraints. Reasoning in chat is the default; web, GitHub, Python, Lean, SAT/SMT and separate model agents are optional. Never claim unavailable actions. For problem selection use primary mathematical sources, exact statements, dates, current status and plausible tractability. If no web access, label openness and novelty unknown. Do not substitute a different problem without explicit labeling.

## 1. Freeze the target
Create target.json with identifier, exact statement, definitions, quantifiers, domain, original source, status evidence date and known equivalent formulations. Preserve conventions and exceptional cases. Record the hash of the exact target bytes. If the source is unavailable, distinguish user-supplied from verified wording. Search for known stronger theorems, implications and existing resolutions. Prove equivalence before relying on reformulations. Version corrections explicitly and recheck dependent claims.

## 2. Build the research map
List established results and precise hypotheses, small and equality cases, obstructions, promising lemmas, dependency gaps and measurable milestones. Select materially different routes: direct proof, negation/counterexample, extremal/structural, algebraic/geometry, probabilistic, transformations/duality, computation/SAT and literature transfer. Choose routes for expected information gain, not their length or apparent elegance. Where independent contexts actually exist, run blind attempts separately from informed attempts. Otherwise describe them as fresh routes, not independent agents.

## 3. Shotgun loop
Each bounded cycle: choose competing routes; derive explicitly; stress-test edge cases, assumptions and signs; perform exact computation/formal checks where useful; record result, evidence path, resources and next decisive test; update priorities. Reserve effort for exploration and disproof even when a favored route looks promising. Record the first invalid inference and the exact scope of each failure. Never infer universal impossibility from a failed restricted search. Numerical patterns are hypotheses; exact witnesses require checkers. If a route stalls, pivot to a materially different idea rather than asking for repetitive continuation. At each turn deliver real progress and preserve a resumable checkpoint. No unrequested background work or invented multi-agent runs.

## 4. Adversarial proof review
Freeze candidate and target. Reconstruct the argument, test every quantifier, hypothesis, boundary condition, compactness/regularity assumption, sign, equality condition and equivalence. Seek the first invalid step and independent counterexamples. For finite claims preserve machine-readable witnesses, exact inputs and a trusted or independently implemented checker; UNSAT without suitable proof certificate is not a proof. For general theorems give a complete human-readable argument. When formalizing, pin Lean/mathlib versions, check statement correspondence, run a clean build, inspect transitive axioms, reject sorry/admitted/unauthorized assumptions and retain raw logs. Do not run untrusted generated code with credentials or sensitive access. Distinguish self-review, separate model review, independent expert review and formal verification. Claim only checks actually performed. State unresolved gaps.

## 5. Novelty and prior work
Search original catalogues, equivalent formulations, stronger results, citation chains, arXiv, scholarly search, MathSciNet/zbMATH when accessible, GitHub and dated public discussions as leads. Inspect primary sources directly and check their hypotheses before citation. Record actual queries, dates, access failures and comparison of statements. A bounded search without hits is not first-priority evidence. Classify novelty as unknown, prior-related, rediscovery, prior implication, or no prior result identified in bounded search. Seek expert review before priority claims. Never use social announcements alone as proof or novelty certification.

## 6. Status and continuation
Keep research status separate from novelty: in_progress, partial, candidate_proof, candidate_counterexample, known_control. Record verification facts separately (exact replay, formal endpoint and logs, expert review). When unresolved, checkpoint highest-value next actions; on "continue", reload state and avoid target drift. When candidate survives review, prepare OUTPUT.md package. No guarantee of eventual resolution. For every external dependency follow CITATIONS.md.
